## D1 · 架构：从 Astro 静态站改成 Go + SQLite

**背景**
第一版用 Astro 7 做纯静态站 + Nginx，零常驻进程，性能很好。需求后来变成“我要能在浏览器里编辑，改完即时生效”。

**评估过的方案**

| 方案 | 结论 | 原因 |
|---|---|---|
| Astro SSG + Decap/Tina CMS | ❌ 否决 | 编辑要经过 commit → 构建 → 发布，延迟 1–2 分钟；且**依赖 GitHub**——实测国内服务器拉 GitHub 多次 TLS 重置，不可靠 |
| Astro SSG + 自建写接口 | ❌ 否决 | 静态站要触发构建才能生效，绕了一圈还是慢 |
| Astro SSR + 数据库 | ❌ 否决 | 保留 Astro 就得保留构建链，复杂度没降下来 |
| **Go 单体 + SQLite** | ✅ **采纳** | 改完刷新就是新的；单二进制 + 单文件数据库；无外部依赖 |

**代价**：丢掉了 Astro 的组件化开发体验，模板要手写 HTML。判断是值得的——这个站的内容结构简单（7 个板块 + 文章），不需要框架的抽象。

**推论**：新项目**不保留任何 Astro 代码**，从零写。

> **v2 更新：虽然还是 Go + SQLite，但不再追求“无构建”的极简**。
> 引入动态渲染后，“编辑→立即生效”不再需要“无构建”这个前提——
> 动态后端本来就没有构建环节。之前否决 SSG 的理由是“要等构建”，这个理由现在不成立了。
> 见 D10。

旧站已于 2026-10-27 全部删除（源码、构建产物、nginx 配置、Node 24、部署脚本），服务器上现在只剩一个占位页。详见《项目说明文档》§8。

## D2 · 权限：做完整的用户与权限体系

> 注意：本条已在 2026-10-27 推翻重写。 原决策是“不做用户系统”，现改为“做”。
> 推翻原因见下方“为什么推翻”。

### 原决策（已废弃）

“不做用户系统、不做登录后换皮，公开页面对所有访客完全一致”。

理由是当时的理解：需求说的是“不要弄成不同用户看到的不一样”。

### 为什么推翻

**第一，那个需求被误读了。** 用户的原话是“我看到的和我分享出去别人看到的不一样，这种才行”。

这句话的重点在**“我分享出去”**——说的是**我**看到的（完整后台）和**我分享给别人的**（一份特定的内容）不一样，不是“所有人的权限分层”。

“不要弄成不同用户看到的不一样”是在**否定“按角色/按会员改变首页内容”这种设计（很多博客会给登录用户隐藏广告、显示专属推荐）。而“我分享出去别人看到的不一样”是在要求**“分享机制”。

这两个诉求并不矛盾，合起来就是：公开页面统一 + 分享内容可控。

第二，也是更重要的原因：项目目标变了。

原方案是“简单、省事”。但用户明确说了这是**用来学习和练手的项目**（vibe coding），“纯静态就没什么学习的必要”。

纯静态 + 单管理员这个组合，恰好把 Web 后端最值得学的东西全绕开了：

| 绕开了 | 学不到 |
|---|---|
| 静态文件 | 会话、登录态、Cookie 安全 |
| 单 Token | 密码哈希、会话表、踢人下线 |
| 无权限 | RBAC、可见性过滤、越权防护 |
| 无附件 | multipart 上传、流式写盘、路径安全、下载鉴权 |
| 无分享 | 令牌生成、授权 Cookie、限流计数 |

而且没有动态后端，上面这些全都学不到。所以 v2 把整个架构推翻重来。

### 新决策

**两级身份 + 一条旁路**：

| 身份 | 能看什么 | 能做什么 |
|---|---|---|
| 访客（任何人，不注册） | 公开已发布内容 | — |
| 站长（owner，唯一账号） | 全部，含草稿和私密 | 编辑内容、生成分享、改设置 |

**旁路：分享链接。任何内容可生成带 token 的链接，可设有效期、访问密码、最大次数。能分享私密内容**。

**核心实现原则：权限判定收口到一个纯函数 `perm.Can(user, action, resource)`，结果塞进 View Model，模板里不写任何权限判断**。

### 为什么只有两级（v2.1 收缩）

第一版设计想的是“匿名 / viewer / editor / owner”四层。实际需求是：**现在只有我和游客**。

- 不做注册 → 没有 `auth/register`、没有注册码、没有用户管理后台
- 不做普通用户 → `visibility` 从三档收缩成两档：`public` / `private`
- 评论本期不做 → 访客连昵称都不用留（见 D6）

**但模型没缩水**：`users` 表、`role` 字段、`perm.Can` 的 Action/Resource 抽象全部保留。
以后想加角色，是加数据 + 改一个 switch，不是重构。

### 推论

- 新增 `internal/perm`、`internal/auth`、`internal/share` 三个包（`internal/attachment` 只留接口，见 D11）
- 站点从静态文件变成 Go 服务端渲染 + SQLite
- 内存开销从 0 变成 ~40MB（2G 机器扛得住，见 D10）

## D4 · 字体：正文仿宋 + Times，标题按配色走

> **v2.8 修订（D23）**：本条原来是「标题和正文都用霞鹜文楷一套」。做阅读页视觉稿时发现霞鹜文楷的拉丁字形是等宽风格的，正文里混排英文（`DevTools`、`location`）像打字机，观感不对。
> 现在改成：**正文用仿宋 + Times New Roman**（都是系统字体，零体积），**标题按配色方案走**——纸间用霞鹜文楷，青空/薄荷用系统黑体。下面保留原来的评估过程。

**评估过**：站酷庆科黄油体（圆润偏可爱）、得意黑（窄体斜切太潮）、站酷快乐体（手写感太活泼）、思源宋体（太正经）。

**原决策**：标题和正文都用霞鹜文楷。理由：
- 它同时是最好读的中文手写体，中文里最有“人味”又最耐读
- 一套字体通吃，不用配第二套标题字，省掉一半字体体积和配对麻烦
- 之前试过“庆科黄油体标题 + 霞鹜文楷正文”的组合，但那个字偏圆润，和整体的冷灰蓝调性不搭

**体积问题：完整 TTF 24 MB。必须按站点实际用到的字符子集化**（实测 345 字 → 64 KB），用 `tools/subset-font.py`。

**v2.2 更正：原稿写“每次改内容后必须重新裁字体，否则新字显示成方框”——缺字不会变方框**，浏览器会回退到系统字体（见 D14）。字体裁剪因此从“改内容就得做”降级成“发布时做一次”。这条已经写进《开发规范》第 8 节和第 12 节。

**v2.8 现状**：正文两种主字体（仿宋、Times）都是系统字体，不打包；霞鹜文楷只剩纸间版标题在用，字集小，裁剪后体积很小。

## D5 · 板块机制：加板块 = 插一行数据库

**需求**：“很多其他板块，每一个板块点进去都可以是一个或者多个页面，以后可以自由新增”

**决策**：
- 板块和子页面存在 `sections` / `section_pages` 表
- 通用路由 `/{section}/` 和 `/{section}/{page}/` 负责渲染
- 加一个板块 = 插一行记录，不改代码、不重启

**早期想法**：用 Astro 的静态路由 + 配置数组生成。那是 SSG 时代的做法，Go + 数据库之后自然变成数据驱动。

**注意：通用路由 `{section}` 必须注册在所有具体路由之后**，否则会吞掉 `/blog/`、`/tags/`。

**v2.1 补充**：板块和子页面都带 `visibility` 字段，只有两档：`public` / `private`。

`private` = 只有站长可见，要给别人看就生成分享链接。

（早期版本这里写的三档 `public` / `members` / `owner` 随 v2.1“不做注册、不做普通用户”一起作废了。）

**v2.2 补充**：板块多了两个字段——`in_nav`（进不进顶栏导航）和 `count_label`（卡片上的计数文案，如“7 篇”）。`about` 因为有专门的 `/about/` 页面，`in_nav = 0`。

## D6 · 评论：本期不做

**决策（2026-10-31）**：**评论区本期不做。** 表、接口、页面、后台审核全都不留，等真要开的时候再加一条迁移。

**理由**：技术笔记站刚开始写，评论区的价值要等有读者才有；而它带一整套成本——反垃圾（蜜罐 + 限流）、审核后台、访客昵称、防刷哈希。先把这些花在还没有内容的地方不划算。

**将来要做时的思路**（已经在《开发规范》§6.7 留了细节，这里记为什么这么设计）：

- 评论存 SQLite，公开可提交
- 三层防护：蜜罐字段 → IP 限流（60 秒 3 条）→ **访客评论一律待审**（`status='pending'`，站长后台放行）
- **不收邮箱**，只存 `sha256(ip + UA + 盐)` 用于防刷（见 D16）
- 楼中楼最多两层

**为什么不接 Giscus**：旧 Astro 站里其实已经接好了 Giscus（`PUBLIC_GISCUS_*` 环境变量开关），它基于 GitHub Discussions，零服务器成本。没选它是因为它依赖 GitHub（同一个理由，见 D1），而且评论存在别人的服务器上。数据在自己手里更可控。

**如果以后想换回 Giscus**：去 [giscus.app](https://giscus.app) 申请，拿 repo / repoId / category / categoryId 四个值，写进环境变量即可。旧的实现已随旧站删除，但这个组件本身只有 20 行，重写比翻旧代码更快。

## D7 · HTTPS：还没解决，换了架构也不影响

**现状：443 端口被 Nginx Proxy Manager（docker）占用，它的证书是废的（`ssl_reject_handshake on`），导致域名走 HTTPS 直接握手失败**（TLS alert 112 "unrecognized name"）。

**已尝试**：certbot HTTP-01 签发——失败。当时的失败原因是 Let's Encrypt 的挑战请求被 **CDN 边缘策略**拦截（403 / "reader size limit exceeded"）。

**2026-10-31 更正：域名现在是直连服务器的，压根没接 CDN。** 也就是说当初 certbot 失败的那个原因已经不存在了，HTTP-01 这条路值得再试一次——前提是先把 443 从 NPM 手里拿回来。

**三条路**（还没选）：

| | 方案 | 成本 |
|---|---|---|
| **A** | 先把 443 从 NPM 拿回来（它上面只剩一个死 Proxy Host），再让宿主 Nginx 直接对外，用 certbot webroot 模式签 Let's Encrypt | 要动 NPM 的 docker 容器，有风险；但没有 CDN 拦挑战，成功率比当初高 |
| B | EdgeOne 控制台申请免费证书（DNS 在 DNSPod 托管可自动验证） | 鼠标点几下，但要把域名挂到 CDN 上，之后就多了一层 |
| C | 继续用 http:// | 零成本，代价是分享链接的密码在传输里是明文 |

**现在的选择是 C（暂不申请）**，理由是站点还没上线、内容还是空的，先把功能做完。

**不解决的后果**：站点只能用 `http://` 访问，功能完全正常，但 Google 收录会受影响，而且分享链接的访问密码是明文过网的。

## D9 · 部署：Go 服务 + systemd + Nginx 反代

**决策**：
- Go 二进制装 `/usr/local/bin/mirage-server`，systemd 托管，监听 `127.0.0.1:8091`
- Nginx 按 Host 分流（`www.miragewzy.online` / `miragewzy.online` → 博客；`119.91.202.143` → tiktok 站）
- 静态资源走 `location ^~ /assets/`，长缓存 + `immutable`
- 80 端口不 301 跳 HTTPS（CDN 回源跟跳会成环）
- 8090 的占位页保留作应急入口，Go 服务另用 8091

**已踩过的 Nginx 坑**（细节见《开发规范》§12）：
1. 哈希资源必须 `location ^~ /assets/`，普通 `location` 会被正则抢走 → `immutable` **静默失效**
2. `add_header` 在子层级会覆盖父层级**全部** `add_header` → 多个安全头要抽 snippet 每处 include
3. 任何改动前 `cp -a` 备份，改完 `nginx -t` 通过才 reload

## D10 · 动态后端：Go 服务端渲染，而不是静态文件

**背景**：v1 选静态 SSG 是因为“简单 + 省资源”。v2 因为学习目标而推翻。

**决策**：Go 服务端渲染 + SQLite，Nginx 反代。

### 为什么这反而是“轻量”的

一个 Go 服务的常驻内存大约 **30–40 MB**（含 SQLite page cache）。这台机器当前：

```
内存 1.9G，可用 1.28G，已加 2G swap
```

新服务占 4% 内存，**完全扛得住**。而且动态后端省掉的是别的东西：

| | 静态 SSG | 动态后端 |
|---|---|---|
| 常驻进程 | 0 | 1（Go） |
| 构建耗时 | 每次发布 2s+ | 0 |
| 外部依赖 | 0 | 0 |
| 附加能力 | 无 | 权限 / 会话 / 附件 / 分享 |

**结论：在 2G 机器上，动态后端是划算的**——用 40MB 内存换一整条可学习的 Web 后端链路。

### 关键约束（否则会翻车）

- **附件必须流式写盘**（将来启用附件时），不能用 `io.ReadAll`——32MB × 几个并发就 OOM
- SQLite 写连接池固定 1 + WAL + `busy_timeout` + 短事务
- **静态资源走 Nginx 直出**，不进 Go 进程（图片、字体、CSS 不该经过应用层，见 D12）
- 模板分段缓存，避免每次请求重新解析
- 渲染耗时打日志，超过 50ms 要能查出来

### 推论

- Nginx 配置要加 `location ^~ /assets/`（静态直出）+ `location /`（反代 Go）
- `client_max_body_size` 要在 server 和 location 两处都写
- 服务器上要有 `/var/lib/mirage/uploads/` 目录，权限 `700`

## D12 · 静态资源：Nginx 直出，模板和迁移才进二进制

**背景**：v2.0 写的是“静态资源用 `embed.FS` 打进二进制，部署只拷一个文件”，同时 §8.3 的 Nginx 配置里又有 `location ^~ /assets/` 直出。两套并存，部署时不知道字体该放哪。

**评估过的方案**

| 方案 | 结论 | 原因 |
|---|---|---|
| 全部 `embed.FS` | 否决 | 图片也要经过 Go 进程，白占内存和带宽；长缓存还是 Nginx 给的，没省掉 |
| 全部 Nginx 直出 | **采纳** | 静态资源本来就要先加工（裁字体、压图、加哈希），产物落在磁盘上，Nginx 直出最自然 |
| CSS/JS embed，图片 Nginx | 否决 | 两种路径两套缓存策略，前缀也容易打架（`/assets/` 和 `/_fonts/`） |

**决策**：

- 静态资源**全部**走 `/assets/` 一个前缀，Nginx `location ^~` 直出，长缓存 `immutable`
- 产物在 `static/public/assets/`（字体、图片、哈希后的 CSS/JS），发布时整目录传上去
- `embed.FS` 只装 `templates/` 和 `migrations/`

**代价**：部署要多传一个目录。换来的是“静态资源不经过 Go 进程”和“前缀只有一套”。

## D13 · 分享链接的授权绑定单个 token

**背景**：分享链接支持访问密码。密码通过后要发一个临时授权 Cookie，免得对方每次都输。

**问题**：一个站可以有很多条分享链接。如果授权 Cookie 是“这个站的一把总钥匙”，它一旦泄露，所有分享链接的内容全都泄露了。

**决策**：授权 Cookie **绑定单条链接**。

- Cookie 名 `mirage_share`，值 `v1.<token>.<过期时间戳>.<HMAC>`
- 签名内容 `share:<token>:<过期时间戳>`，用 `MIRAGE_SECRET` 算
- 服务端只认“签名对得上、token 也对得上”的那一条链接
- **不把 token 本身当凭证**：那等于“拿到 Cookie 就等于过了密码”
- TTL 2 小时

**顺带定的：`max_visits` 限制的是密码校验通过**的次数，不是访问次数。凭 Cookie 的免密访问不计数——否则“输一次密码看十次”和“最多 3 次”自相矛盾。

## D14 · 字体子集是发布期产物，不阻塞内容发布

**背景**：v2.0 写的是“改了内容必须重新裁字体，否则新字显示成方框”，这跟“改完刷新就是新的”直接打架。

**更正**：缺字**不会**显示成方框。裁剪后的字体没有某个字形时，浏览器按 `font-family` 链回退到系统字体（PingFang SC / 微软雅黑 / system-ui），中文系统字体一定有这个字，最多就是那一两个字跟正文不是一个字体。

**决策**：

- 字体子集是**发布期产物**，`make build` 时裁一次，产物进 `static/public/assets/fonts/`
- 内容改动即时生效，不受字体影响
- 新字在下一次发布时统一，不想等就手动跑一次裁剪命令
- 裁剪脚本必须扫 `templates/`（Go 模板是 `.html`），否则模板用字不在子集里

**推论**：“改了内容必须重裁字体”从“硬要求”降级成“下次发布顺手做”。

## D19 · 开发期约定（2026-10-31）

**背景**：动手写第一行代码之前，有六件事不定下来，后面每一行代码都要回来改一遍。

**决策**：

| 项 | 决定 |
|---|---|
| 代码放哪 | 代码托管在 **GitHub**（私有库）。发布走本地构建 + `scp`，服务器不拉代码 |
| 配置怎么读 | 纯 env + flag 兜底，优先级 flag > env > 默认值 |
| 数据库路径 | 同样三级优先：`-db` > `MIRAGE_DB` > `data.db` |
| 本地静态资源 | 加 `-dev` 开关，开发时 Go 直接把 `static/src` 发在 `/assets/` 下；生产仍然 Nginx 直出 |
| 日志 | 只写 stdout，不自己写文件。生产由 journald 收，自带轮转 |
| M1 验收 | `/healthz` 200 + JSON、优雅退出、常驻内存 < 40MB、日志结构化 |

**为什么这么定**：

- **flag 只给临时覆盖用**，固化配置走环境变量。生产的配置在 systemd 的 `EnvironmentFile` 里，一份配置两处用
- **密钥不给 flag**。命令行参数在 `ps` 里是明文，密钥只能走环境变量或文件
- **默认值要保证最简启动能跑**。`go run ./cmd/mirage-server` 不带参数就该起来，不然后面每次调试都要先准备环境
- **开发模式和生产只差「静态资源谁发」这一处**。URL 形状保持一致（`/assets/css/app.css`），模板里只写 `{{ asset "css/app.css" }}`，两种模式的差别由 `internal/assets` 内部消化
- **日志只写 stdout**。自己写文件就要自己配 logrotate，systemd 的 journald 免费给你轮转、按用户过滤、按时间切

**M1 要做成什么样**：

- `/healthz` 返回 200 + JSON
- SIGINT / SIGTERM 能优雅退出（等在途请求做完，最多等 5 秒）
- 常驻内存（`ps RSS`）< 40 MB
- 日志是结构化的，能被 journald 和日志检索直接吃

**推论**：`MIRAGE_SECRET` 缺失时 M1 只警告不拒绝启动（那时候还没签名逻辑），M5 起改成硬失败。

**一条已经验证过的事实**（写代码时试出来的）：常驻内存和提交内存差很多——Windows 上 WorkingSet 8.2 MB、Private 44 MB，`ps RSS` 对应的是常驻那个。别拿错指标下结论。

## D20 · 数据层：四张表起步，迁移只管结构

**背景**：M2 是数据层。有一件事先说清楚：**迁移不是搬数据，是管表结构的版本**。站上的数据从零开始写，但表结构会一直变——今天建 `posts` 表，十天后加 `reading_minutes`，二十天后加 `cover`，三十天后加索引。每一次改结构都是一次迁移，写进 `migrations/NNN_xxx.sql`，数据库里用 `schema_migrations` 记着跑到第几号了。

**决策**：

| 项 | 决定 |
|---|---|
| 建几张表 | 先建 4 张核心表：users / sessions / sections / posts。其余 6 张用到时再迁移 |
| 迁移形态 | 只支持 `.sql` 文件，不预留 Go 迁移。以后真有需要再加，不用改架构 |
| 谁来跑迁移 | 开发和生产**都自动跑**，启动时把没跑过的按顺序执行。跑失败**拒绝启动**，不带着半截 schema 继续跑 |
| 写怎么串行 | 两个连接池：读池 4 个连接、写池 1 个连接，两条独立的 `*sql.DB` 指向同一个文件 |
| 验收 | 迁移器能跑、幂等重跑不报错、`journal_mode` 确认是 wal、四张表都建出来、store 方法有单测（临时文件库） |

**为什么这么定**：

- **先建 4 张表**。一次建 10 张，第一次跑就面对一大张 schema，出问题很难定位是哪张表的锅。剩下的是 attachments / share_links / settings / section_pages 这些附属表，用到时迁移更省事（**评论表已经去掉了**，见 D6）
- **两边都自动跑**。开发时改了 schema 启动就行，省一个命令；生产也自动是因为迁移在事务里执行，SQLite 的 DDL 是事务性的，失败会整体回滚，不会留下半截 schema。真正的保险是**备份**（§8.4 每天一次）和**迁移只增不改**
- **写池固定 1**。SQLite 整库级写锁，同时只有一个写者。写连接池只有 1 个连接，写就天然串行了，不用靠事务排队，也不会出现 `database is locked`

**推论**：

- `posts.section` 不加外键。板块 slug 会被改名，加了外键以后改名要连带改一堆文章，现在的做法是文章里存 slug 字符串
- `schema_migrations` 表由迁移器自己建（`CREATE TABLE IF NOT EXISTS`），不写在迁移文件里——它得在读「已执行哪些迁移」之前就存在
- 权限过滤不用 `1 = 1` 表示「不过滤」，`perm.VisibilityFilter.SQL()` 返回空串表示不过滤，由 store 决定要不要拼 WHERE（`1=1` 会让 SQLite 走全表扫描）

## D22 · 配色方案：每日一换，只有站长能切

**背景**：D21 把主题方向定成「清新」。后来做了三版配色方案（纸间 / 青空 / 薄荷）摆出来看，三版都觉得好，舍不得只选一版。于是问题变成：怎么让三版共存，又不把站点搞得花。

**决策**：

| 项 | 决定 |
|---|---|
| 轮换方式 | **一天一换**，不是几秒一换。白天读文章时颜色不能一直跳 |
| 切换权限 | **访客没有任何配色入口**，只有站长能切 |
| 站长入口 | 登录后顶栏一个**小色点**，点开浮层：跟随日期 / 纸间 / 青空 / 薄荷。选完存 Cookie，只影响他自己 |
| 站点级覆盖 | `settings.theme_today`（`auto` / `paper` / `sky` / `mint`），站长在后台钉死一版，对所有访客生效 |
| 明暗模式 | 独立的一个轴，**访客也能切**（☾ 按钮）。暗色只有一套，不随配色方案变 |

**优先级**：

```
个人偏好（站长的 Cookie）> 站点设置 settings.theme_today > 按日期自动
```

**为什么这么定**：

- **一天一换，不是几秒一换**。几秒一换看着热闹，实际阅读时一直在变，眼睛累。换成一天一版，访客每次来可能都是新样子，但坐下来就稳定了
- **访客不给入口**。这个站本来就小气，访客界面越干净越好。访客看到的永远是当天那版，这是站主的审美，不是访客要操心的事
- **服务端定方案**。服务端按日期（或站点设置）算出今天该用哪版，直接渲染成 `<html data-theme="mint">`。首屏就对、不闪白，而且访客禁用 JS 也是对的配色——JS 只管浮层交互
- **个人偏好用 Cookie 不写库**。它只是「我今天想看纸间」，不是站点状态。写库就得建表、得清理、还得考虑多设备
- **暗色不跟着方案变**。三套方案只影响亮色，否则工作量翻三倍，而暗色是少数场景

**踩过的坑**：原来 `data-theme` 这个属性名是给暗色模式用的（`[data-theme="dark"]`）。加配色方案后两个轴撞名了，改成：

| 轴 | 属性 | 取值 |
|---|---|---|
| 明暗 | `data-mode` | `light` / `dark` |
| 配色方案 | `data-theme` | `paper` / `sky` / `mint` |

localStorage 的键也跟着分开：`mirage-mode`（明暗）和 `mirage_theme`（配色，Cookie）。

**推论**：

- 三套方案在 `tokens.css` 里各一组 `[data-theme="xxx"]` 变量，覆盖亮色默认值；间距、字号、阴影、字体栈三版共用
- URL 参数 `?theme=paper` **只对登录的站长生效**（服务端判断），用来快速预览某版
- 配色浮层按钮由服务端按身份决定是否渲染——访客的 HTML 里连这个按钮都没有

## D23 · 阅读页：正文仿宋 + Times，h2 加短横线标记

**背景**：配色方案定完之后，阅读页还没验过。做了三版配色下的文章详情页视觉稿，发现两个文档跟实际对不上的地方。

**决策**：

| 项 | 决定 |
|---|---|
| 正文字体 | **Times New Roman（拉丁）+ 仿宋（中文）**，三版配色共用 |
| 标题字体 | 跟配色方案走：纸间用霞鹜文楷，青空/薄荷用系统黑体（700） |
| 正文字号 | 16.5px → **17px** |
| h2 层级 | 19px → **21px**，并在上方加一条 **26px 宽的强调色短横线** |
| 文章标题 | 上限 40px → **36px** |
| h3 | 17px → 17.5px |

**为什么这么定**：

- **字体栈把 Times 放第一位**。浏览器按字符找字体：拉丁字母和数字 Times 有，就它渲染；中文 Times 没有，落到后面的仿宋。一条栈同时管住两种文字，不用拆 `unicode-range`
- **标题不跟正文统一，但每版内部统一**。黑体标题 + 仿宋正文是中文公文的标准搭配，楷体标题 + 仿宋正文是书籍的搭配，都不打架；但楷体标题 + 黑体正文会打架——手写楷体配机械黑体，像两套设计
- **正文提到 17px**。仿宋笔画比黑体细，同字号下显小一号。17px 才相当于原来黑体的 16.5px
- **h2 加短横线**。19px 标题跟 16.5px 正文差得太少，纸间用楷体时几乎看不出是标题。加一条短横线当**小节标记**——它标的是「这里开始新的一节」，是结构信号不是装饰。三版通用
- **h1 降到 36px**。40px 粗黑体压在 44em（720px）正文宽里太凶，占两行。纸间楷体 40px 好看，但黑体版明显过重，取 36px 两版都不出错

**踩的坑：仿宋不能打包**。仿宋（FangSong）是中易的商业字体，**不可再分发**，只能靠系统自带。Windows / macOS 有，Android / iOS 没有，会退到 `Noto Serif CJK SC` 之类的衬线字——观感接近但不完全一样。这是「正文零字体体积」的代价，接受。

**推论**：

- 正文两种主字体都是系统字体 → **正文零字体文件**，首屏不受字体影响。霞鹜文楷只出现在纸间版标题里，字集小，裁剪后体积很小
- 纸间版标题到底用不用霞鹜文楷，**留到做那版主题时再定**。不用的话全站零字体文件；用的话多背几十 KB 换一个手作感。不影响现在写代码
- 字号阶梯表和 §5.3 的页面结构图同步改了，写代码时对着新数值
- 代码块右上角的「复制」按钮：默认透明，hover 代码块才出现（不干扰阅读）
- 目录在桌面端是右侧 sticky 栏（216px），**可收缩**——收起时整列消失、正文重新居中，右边缘留一个竖排「目录」标签随时拉回来；状态存 `localStorage`（`mirage-toc`），翻页不丢。移动端是标题下方的 `<details>`，每次默认合上
